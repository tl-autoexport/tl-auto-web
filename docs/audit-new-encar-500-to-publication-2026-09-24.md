## 2. Что хотели сделать

Задача была получить 500 новых объявлений Encar, которых ещё нет в `cars`, затем:

1. собрать максимально полный набор данных Encar;
2. сохранить результат отдельно, без автоматической публикации;
3. определить мощность через согласованную цепочку источников;
4. разрешить предварительную мощность, если точную подтвердить не удалось;
5. пересчитать цену по действующим ставкам;
6. проверить актуальность объявлений через Encar;
7. исключить дубли, тестовые записи, проданные и недоступные машины;
8. опубликовать только прошедшие контракт публикации карточки.

Ключевое ограничение: enrichment и публикация должны быть разными этапами. Получение данных не должно автоматически создавать публичную карточку.

## 3. Сбор кандидатов

### Первая попытка

Первая команда была запущена с маленьким лимитом страниц. Encar вернул недостаточно уникальных новых записей:

```text
Only 48 new candidates passed discovery; target is 50. No staging run was created.
```

Это поведение было правильным: система не создала неполную партию под видом полного прогона.

### Попытка на 500

При первом запуске с целью 500 удалось найти 152 новых кандидата. Причина — ограничение глубины просмотра списка и фильтры свежести.

После увеличения диапазона:

```bash
CATALOG_MAX_LISTING_AGE_DAYS=365 \
ENCAR_NEW_STAGING_TARGET=500 \
ENCAR_NEW_STAGING_MAX_PAGES=60 \
npm run stage:new-encar-candidates
```

получен результат:

```text
checked=625 accepted=493
...
candidate_count: 500
freshCandidates: 2110
```

Создан staging run:

```text
f7e9cca4-33ca-4813-9152-b6d4f42045b9
status: awaiting_approval -> approved
candidate_count: 500
```

### Важное исправление в сборщике

Скрипт `stage-new-encar-candidates.ts` был добавлен как отдельный read-only discovery-путь. Он:

- ищет только ID, которых нет в `cars`;
- не вставляет строки в `cars`;
- создаёт run и очередь enrichment;
- сохраняет исходный кандидат с URL, маркой, моделью и годом;
- не публикует карточку.

При последующем прогоне выяснилось, что назначение `purpose` должно соответствовать DB check constraint. Значение, использованное в первой версии, не принималось ограничением `encar_enrichment_runs_purpose_check`. Это было исправлено на допустимый `full`.

## 4. Обогащение Encar

В очередь попало 500 задач. Для каждой задачи worker запрашивал отдельные блоки:

- `inspection` — диагностика;
- `summary` — сводные данные;
- `options` — комплектация;
- `detail` — основная карточка и галерея;
- `diagnosis`;
- `sellingpoint`;
- `contents` — полная комплектация;
- `history` — открытая история.

Результаты сохранялись в:

- `encar_enrichment_queue` — статус обработки;
- `encar_enrichment_staging` — payload и результаты блоков;
- `encar_enrichment_runs` — описание партии.

После worker:

```text
succeeded: 498
unavailable: 2
```

В staging сохранены все 500 строк, включая недоступные результаты. Это важно для аудита: запись о неудачной попытке не исчезает.

## 5. Почему worker несколько раз останавливался

### 5.1. Обычная SSH-команда не была фоновым сервисом

Первые запуски выполнялись через обычный терминал VPS. Когда окно закрывалось или истекал timeout, процесс Node завершался. В базе оставались записи со статусом `leased`, хотя worker уже не работал.

Из-за этого создавалось впечатление зависания:

```text
leased: 79
queued: 175
succeeded: 244
```

При этом процесса уже не было:

```text
pgrep -af "run-universal-encar-enrichment"
```

ничего не возвращал.

### 5.2. Истёкшие lease не возвращались автоматически

Проверка показала:

```text
leased_total: 79
expired_ready_to_retry: 79
still_active: 0
```

После ручного возврата в `queued` запускали worker повторно. Два параллельных запуска также были ошибкой эксплуатации: оба процесса пытались забирать одну и ту же очередь.

### 5.3. `nohup` скрывал фактическое состояние

`nohup` оставлял оболочку и Node в фоне, но не давал полноценного контроля жизненного цикла. При повторных командах появлялись несколько процессов или старые lease.

### 5.4. Исправление через systemd

Добавлен шаблон:

```text
deploy/systemd/tl-auto-encar-enrichment@.service
```

Worker стал запускаться как отдельный сервис на конкретный `run_id`:

```bash
sudo systemctl start tl-auto-encar-enrichment@RUN_ID
sudo systemctl status tl-auto-encar-enrichment@RUN_ID --no-pager
sudo journalctl -u tl-auto-encar-enrichment@RUN_ID -f
```

Добавлены:

- восстановление stale lock;
- lease timeout;
- heartbeat и события `item_completed`;
- корректная остановка по SIGTERM;
- журнал в `journalctl`;
- защита от второго worker на ту же партию.

### 5.5. Финальная ошибка worker

После успешной обработки всех 74 задач refresh-worker завершился с ошибкой:

```text
TypeError: Cannot read properties of null (reading 'encarId')
```

Ошибка произошла в финальной ветке worker после обработки данных, а не при запросе Encar. Статусы очереди показали, что все 74 строки имеют `succeeded`, поэтому данные не потерялись. Это отдельный дефект завершения worker, который нужно исправить: итоговый отчёт должен безопасно обрабатывать пустой результат последнего элемента.

## 6. Первый скрининг и ошибка в критерии полноты

Первый скрининг дал:

```text

manualReview: 235
unavailable: 2
```

Причиной manual review были отсутствующие дополнительные блоки:

```text

insurance: 172
history: 162

```

Проблема была в том, что полнота enrichment ошибочно воспринималась как обязательная готовность к расчёту. Это смешивало два разных понятия:

- наличие основной карточки, цены, года, двигателя, топлива, галереи и мощности;
- наличие необязательных диагностических и исторических блоков.

Скрининг был изменён. После исправления:

```text

partialEnrichment: 235
needsPowerReview: 1
unavailable: 2
```

Теперь неполная диагностика не блокирует карточку, если обязательные данные для цены и мощности есть. Дополнительные блоки сохраняются как enrichment staging и могут применяться позже.

## 7. Разбор мощности

### Первоначальный план

План мощности сначала дал:

```text
approved_match: 0
unmatched: 497
needs_source_retry: 1
```

Это было неверное измерение, а не отсутствие мощности. Причина: refresh-run создавался по одним ID, а в `candidate_snapshot` не было года. Год находился в свежем payload Encar:

```text
detail.category.formYear
detail.category.yearMonth
```

Исправлен `scripts/plan-new-encar-power-resolution.ts`: год теперь берётся из актуальной категории Encar, если его нет в первоначальном snapshot.

После исправления:

```text
approved_match: 305
unmatched: 191
```

В approved-подмножестве:

```text
T1: 243
T2: 47
T3: 4
```

Это показывает, что основная ошибка была в неполном входном контексте, а не в отсутствии записей справочника.

### AutoHome

Для 191 конфигурации был добавлен read-only запрос к AutoHome:

```text
seriesRequested: 11
seriesWithSpecs: 9
candidateSpecs: 259
mappedConfigurations: 26
unmappedConfigurations: 102
```

Matcher дал:

```text
no_match: 31
review: 3
ambiguous: 5
```

Проблемы AutoHome:

- часть моделей отсутствовала в источнике;
- для части не совпадал год;
- для части не совпадал объём двигателя;
- часть имела несколько возможных мощностей;
- редкие модели требовали более мягкого сопоставления.

После нормализации названий и года утверждённых совпадений стало 305.

### Предварительная мощность

Было принято решение не отбрасывать весь остаток при отсутствии точного заводского совпадения. Для конфигураций с единственным подходящим предварительным правилом использовался `vehicle_power_automatic_reference`.

Предварительная мощность:

- сохраняется с отдельным классом уверенности;
- не становится подтверждённой спецификацией;
- участвует в расчёте только как `matched`;
- отображается как предварительный расчёт на детальной странице;
- может быть заменена после появления более точного источника.

ИИ и внешние источники также были добавлены в исследовательскую цепочку, но результат не должен влиять на цену напрямую без сохранённого доказательства и контролируемого статуса.

## 8. Почему появилась отдельная live-проверка 74

Для исходных 491 была сделана предыдущая live-проверка:

```text
477 active
14 unavailable
```

Из активных:

```text
295 approved
182 preliminary
```

Повторно были выбраны 74 записи с изменением цены или основной конфигурации:

- 36 с изменением цены;
- 42 с изменением модели или конфигурации;
- 4 входили в обе группы.

Итого: `36 + 42 - 4 = 74`.

Проверка 74 была нужна, чтобы не публиковать расчёт, построенный на старой цене или старой модели. Она не была новой партией объявлений и не должна была заменять исходный итог 491.

В live-данных обнаружились важные флаги Encar:

- `manage.dummy = true` — тестовая или дублирующая карточка;
- `advertisement.salesStatus = CONTRACT` — объявление уже продано или оформляется;
- `advertisement.status = ADVERTISE` — одного этого поля недостаточно для решения о публикации.

Два подозрительных объявления с ценой `99 980 000 KRW` оказались связанными с одним автомобилем и статусом `CONTRACT`. Они исключены.

## 9. Почему итог изменился с 491 до 311

Для исходной партии 491 были объединены:

- исходный силовой план;
- предварительные совпадения;
- свежие данные 74;
- флаги `dummy` и `CONTRACT` из сохранённых payload;
- 14 ID, которые live-проверка назвала недоступными;
- проверка уже существующего каталога по номеру автомобиля.

Итоговый расчёт:

| Причина | Количество исключённых строк |
|---|---:|
| `dummy` | 152 |
| `CONTRACT` после исключения dummy | 11 |
| Мощность перестала сопоставляться после обновления | 8 |
| Недоступны и ещё не исключены другой причиной | 9 |
| Всего исключено | **180** |
| Осталось к публикации | **311** |

Причины не складывались наивно: одна карточка могла одновременно быть `dummy`, `CONTRACT` и входить в список недоступных. Сначала строилось множество ID, затем применялся один итоговый статус.

Из 311:

```text
191 approved
120 preliminary
```

Однако 9 из 311 уже имели активную карточку в `cars` под другим источником `chestny_prigon`. При повторной вставке возник бы дубль. Поэтому:

```text
311 кандидатов
- 9 уже представленных по номеру автомобиля
= 302 новые карточки
```

## 10. Почему публикация заняла много времени

Основная причина — несколько независимых смыслов были изначально смешаны в одну проверку:

1. полнота enrichment;
2. наличие мощности;
3. точность мощности;
4. актуальность объявления;
5. отсутствие дубля;
6. готовность расчёта;
7. готовность к публикации.

Из-за этого происходили повторные круги:

- enrichment считался неполным из-за отсутствия необязательной диагностики;
- planner не находил год и искусственно превращал почти всю партию в unmatched;
- старый worker зависал после закрытия SSH-сессии;
- lease оставались активными после смерти процесса;
- `nohup` запускал несколько конкурирующих workers;
- live-check проверял `status`, но не учитывал `dummy` и `salesStatus`;
- 74 refresh ошибочно начали восприниматься как новая партия вместо проверки части 491;
- старый импорт был непригоден для публикации этой группы, потому что мог заново определить мощность;
- первый отчёт не различал публикационный блокер и отсутствие необязательного блока;
- дубли по номеру автомобиля проявились только на финальной проверке записи.

Таким образом, время ушло не на сам Encar-запрос, а на исправление границ между этапами и на доказательство того, что каждое число относится к одной и той же группе объявлений.

## 11. Что было изменено в коде и базе

### Публикационный контракт

В проекте закреплены проверки:

- цена требует месяц расчёта;
- цена требует resolved power status;
- мощность требует `power_basis`;
- `power_resolution_source` обязателен для публикационного расчёта;
- дата публикации имеет источник;
- `catalog_added_at` фиксирует внутреннее добавление в каталог;
- `encar_enrichment_status` имеет отдельную семантику;
- предварительная мощность не считается финальной.

Использованные миграции:

- `20260919_calculation_contract.sql`;
- `20260919_calculation_contract_scope.sql`;
- `20260920_price_requires_month.sql`;
- `20260921_ai_evidence_link.sql`;
- `20260922_canonical_provenance_invariant.sql`;
- `20260922_canonical_provenance_validate.sql`;
- `20260922_catalog_added_at.sql`;
- `20260922_published_at_provenance_and_enrichment_status.sql`.

### Дата публикации

Выяснилось, что в payload Encar нет надёжной даты публикации, пригодной для подписи «В продаже N дней в Корее». Поэтому:

- `published_at` не заполняется нашим временем;
- `published_at_source = unknown`, если нет даты источника;
- внутреннее время хранится отдельно в `catalog_added_at`;
- интерфейс не подставляет `created_at` в срок продажи в Корее;
- блок срока скрывается, если дата источника не подтверждена.

### Enrichment статус

Поле `cars.enrichment_status` уже имело другую семантику, поэтому добавлен отдельный `encar_enrichment_status` со значениями:

- `applied`;
- `available_not_applied`;
- `absent`;
- `unavailable`.

Это не позволяет смешивать статус обогащения с объединением источников или состоянием карточки.

### Power reference и AI

Добавлены и изменены:

- нормализация конфигурации автомобиля;
- расширенный matcher года, объёма, топлива, привода и комплектации;
- AutoHome worklist и matcher;
- классификация `vehicle_power_automatic_reference`;
- предварительные reference для разрешённых конфигураций;
- AI wave scripts для исследования мощности;
- сохранение evidence и confidence;
- отдельный путь для предварительной мощности.

Принцип: AI или fallback не пишет цену напрямую. Сначала создаётся результат с источником и статусом, затем он участвует в расчёте согласно confidence.

### Durable worker

Изменения по worker проходили отдельными коммитами:

- `b9295c7` — durable worker;
- `f430333` — запуск через systemd;
- `6998e9a` — повтор transient proxy failures;
- `23f...` — stale lease recovery и heartbeat в актуальной ветке;
- `3ff3cb9` — отдельный безопасный публикатор партии.

Фактический шаблон systemd находится в `deploy/systemd/tl-auto-encar-enrichment@.service`.

## 12. Новый публикатор

Для этой партии создан:

```text
scripts/publish-new-encar-cohort.ts
```

Он отличается от общего Encar importer тем, что:

- читает только согласованные staging runs;
- не делает новый запрос к Encar;
- не меняет уже существующие карточки;
- повторно проверяет допустимый класс мощности;
- исключает `dummy` и `CONTRACT`;
- исключает недоступные ID;
- проверяет дубли по номеру автомобиля;
- блокирует запуск при изменении состава партии;
- использует advisory lock;
- пишет карточку, snapshot, media, options, condition report и calc snapshot в одной DB-транзакции;
- проверяет количество карточек, snapshot и media перед commit;
- поддерживает dry-run и probe режим.

Пробный режим записал одну карточку внутри транзакции и откатил её. После этого выполнена реальная публикация.

## 14. Ошибки процесса, которые нужно исправить

### 14.1. Один run ID должен использоваться на всём пути

Каждый отчёт, план, screening и публикация должны проверять совпадение `run_id`. Нельзя сравнивать числа из разных запусков по времени создания.

### 14.2. Нужен единый publication readiness report

Сейчас readiness, power plan, live-check и duplicate-check существовали отдельными инструментами. Нужен один итоговый отчёт с полями:

```text
source_listing_id
power_class
power_source
enrichment_status
live_status
dummy
sales_status
duplicate_status
calculation_status
publication_status
blockers[]
```

Это исключит ручное сложение результатов разных файлов.

### 14.3. Live-check должен сразу проверять Encar flags

В live-check нужно добавить:

- `manage.dummy`;
- `manage.dummyVehicleId`;
- `advertisement.salesStatus`;
- `vehicleNo`;
- актуальные фото и цену.

Проверка только `advertisement.status = ADVERTISE` недостаточна.

### 14.4. Worker должен завершаться чисто после последней записи

Нужно исправить финальную ошибку `idOf(null).encarId`, чтобы завершение всех элементов не переводило сервис в `failed` после фактически успешной обработки.

### 14.5. Lease должны восстанавливаться в DB-функции

Сейчас часть восстановления происходила worker-ом. Надёжнее сделать claim RPC, которая атомарно:

1. возвращает истёкшие lease в `queued`;
2. выбирает следующую пачку;
3. ставит новый lease;
4. возвращает rows worker-у.

### 14.6. Нужно заранее различать новые и существующие карточки

Перед финальной публикацией требуется проверить одновременно:

- `(primary_source, source_id)`;
- `vehicle_no_masked` среди активных карточек;
- VIN, если он есть;
- source URL.

Эта проверка должна выполняться в публикаторе до подготовки транзакции, а не обнаруживаться в самом конце вручную.

### 14.7. Данные из optional enrichment не должны блокировать публикацию

Нужны два статуса:

- `core_ready` — цена, мощность, источник, фото, расчёт;
- `optional_enrichment` — диагностика, история, insurance, options, selling points.

Отсутствие optional блока должно оставлять задачу на последующее enrichment, но не превращать карточку в неподготовленную, если core contract выполнен.

### 14.8. Публикация должна запускаться только через один скрипт

Нельзя использовать общий importer для публикации партии, где мощность уже согласована отдельным планом. Общий importer может повторно разрешить мощность другим правилом.

Для будущих партий нужен единый CLI:

```bash
npm run publish:new-encar -- \
  --run-id RUN_ID \
  --mode dry-run

npm run publish:new-encar -- \
  --run-id RUN_ID \
  --mode publish
```

Команда должна выдавать один итоговый JSON и требовать совпадения ожидаемого состава.

## 15. Рекомендуемый следующий процесс

Для следующей партии порядок должен быть таким:

1. Discovery создаёт run, но не пишет в `cars`.
2. Approval переводит run в `approved`.
3. Один durable systemd worker обрабатывает очередь.
4. Screening разделяет `core_ready` и `optional_partial`.
5. Power planner формирует approved и preliminary классы.
6. Live-check проверяет availability, price, model, dummy, contract и vehicle number.
7. Duplicate audit проверяет источник, номер и VIN.
8. Единственный publication planner создаёт allowlist.
9. Dry-run показывает точные counts и blockers.
10. Probe записывает одну карточку и откатывает транзакцию.
11. Publish пишет весь allowlist одной транзакцией.
12. Post-publish audit проверяет cars, snapshots, media, prices, month и publication contract.

## 16. Главный вывод

Проблема была не в том, что Encar не отдавал данные. Данные были получены: 498 из 500 enrichment-задач завершились успешно, а 302 карточки в итоге прошли полный путь.

Основные потери времени возникли из-за отсутствия одного общего контракта между discovery, enrichment, power resolution, live-check и publication. Каждый этап имел собственное число кандидатов и собственный смысл слова «готово». Поэтому приходилось вручную доказывать, что результаты относятся к одной партии и не содержат дублей.

После этого прогона основные защитные механизмы уже появились:

- отдельный staging;
- durable worker;
- явные lease и retry;
- разделение core и optional enrichment;
- confirmed и preliminary power;
- live-check;
- проверка dummy и contract;
- проверка дублей;
- DB-инварианты цены и месяца;
- единый безопасный публикатор;
- атомарная транзакция и post-publish audit.

Следующее улучшение должно быть направлено на объединение этих проверок в один воспроизводимый publication plan. Тогда следующая партия не должна занимать несколько дней: система должна выдать один allowlist, список блокеров и готовый к запуску publish command.
